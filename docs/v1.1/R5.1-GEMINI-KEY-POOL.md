# R5.1 — Pool de keys Gemini

Base autorizada: `399cd9d`, rama `feat/v1.1-natural-router`.
Sin deploy, merge, cambios a Evolution, Policy, Tool Registry ni reglas R5.

## Plan del ajuste

1. Validar keys y protecciones locales desde entorno, conservando aliases.
2. Compartir un pool en memoria entre adapters del proceso, con rotación justa.
3. Aplicar cooldown/failover secuencial y una pasada máxima por llamada lógica.
4. Limitar concurrencia con cola FIFO; conservar presupuestos lógicos del turno.
5. Mantener accounting existente por intento y diagnóstico sin secretos.
6. Probar pool, cuotas, adapter y R5/ledger; ejecutar checks y push; detenerse.


## Configuración

Todas las credenciales siguen exclusivamente en entorno/`.env` privado; no se
escriben keys, hashes ni fragmentos en PostgreSQL, snapshots, logs o diagnóstico.
El adaptador necesita material de autenticación en memoria privada para el header
`x-goog-api-key`; el estado público solo tiene índices y labels `gemini-key-N`.
No pegar valores reales en documentación ni en comandos compartidos.

| Variable | Default / regla |
|---|---|
| `GEMINI_API_KEYS` | Lista separada por comas: trim, quitar vacías, deduplicar conservando orden. Tiene precedencia. |
| `GEMINI_API_KEY` | Legacy; se usa si la lista anterior queda vacía. |
| `GEMINI_FREE_TIER_CONFIRMED` | `false`; activar solo tras confirmar **todos** los proyectos sin facturación vinculada. No cambia ni activa billing. |
| `LLM_LOCAL_DAILY_LIMIT` | `0`: sin límite diario local. |
| `LLM_LOCAL_GLOBAL_RPM` | `0`: sin RPM global local. |
| `LLM_LOCAL_USER_RPM` | `0`: sin RPM local por actor. |
| `LLM_MAX_CONCURRENT_CALLS` | `4`; entero entre 1 y 32 por proceso. |
| `LLM_INPUT_TOKENS_PER_MINUTE` | `0`: sin TPM local; se puede fijar una protección positiva. |
| `LLM_RESERVED_INPUT_TOKENS` | `32768`; reserva fallback existente, no cuota Google. |

Se falla al iniciar si no queda ninguna key, incluso con Gemini deshabilitado;
la configuración inválida solo enumera nombres de variables. Se validan valores opacos
aptos para el header (ASCII visible, sin espacios, controles ni comas internas),
sin fijar prefijo/longitud/formato Google ni rechazar placeholders de tests. La autenticidad la valida Google.
Una lista no vacía inválida falla; no se esconde detrás del fallback legacy.

Precedencia local: `LLM_LOCAL_*` > `LLM_*` históricos > `GEMINI_*` históricos >
defaults. Los aliases siguen admitiendo valores positivos explícitos y ahora cero.
Un alias malformado sigue siendo error aunque otro nombre tenga precedencia.
Vacíos, negativos, decimales y valores fuera del rango configurado fallan.
`LLM_RESERVED_INPUT_TOKENS` conserva mínimo 1. Los máximos de validación existentes
son protecciones de configuración, no supuestos de cuotas del proveedor.

**Entornos existentes:** un `LLM_DAILY_LIMIT=20` o `GEMINI_DAILY_LIMIT=20` explícito
sigue siendo respetado. Para Lab, configurar `LLM_LOCAL_DAILY_LIMIT=0`,
`LLM_LOCAL_GLOBAL_RPM=0`, `LLM_LOCAL_USER_RPM=0`; si existía TPM local bajo,
`LLM_INPUT_TOKENS_PER_MINUTE=0`. Este trabajo no modifica `.env` ni despliega.
Compose propaga las variables a app/worker; `.env.example` contiene solo defaults.

## Selección y failover

Un `GeminiKeyPool` compartido por el objeto Config de cada proceso sirve a todos
los adapters/actores: no se crea un pool nuevo por mensaje. Round-robin recorre
keys saludables, omite cooldowns y distribuye uniformemente las llamadas normales.
La selección ocurre al obtener turno en la cola, evitando elegir una key que se
haya enfriado mientras esperaba. No hay solicitudes especulativas o paralelas por
una misma llamada lógica. Cada key se intenta como máximo una vez en esa llamada.

Estado por índice: available, cooldownUntil, consecutive429, consecutiveErrors,
lastUsedAt, requests, successes, rateLimited y failures. `available=false` significa
credencial deshabilitada; el diagnóstico separa saludables, listas y en cooldown.
Una key en cooldown vuelve a ser elegible al vencer, sin una llamada de sondeo.
El éxito reinicia las rachas de errores. Todo este estado se reinicia con el proceso.

- `429`: enfriar la key y probar otra elegible dentro de la misma llamada lógica.
  `Retry-After` acepta delta-seconds o fecha HTTP, sin acortar un plazo válido.
  Sin header válido: 60 s, 120 s, 240 s… hasta 15 min. No se espera ni se insiste
  sobre esa key durante el cooldown.
- `401`/`403`: deshabilitar inmediatamente durante el proceso y probar otra key.
  No se bombardea una credencial inválida. Google `400` con metadata oficial
  `API_KEY_INVALID` recibe el mismo tratamiento; otros `400` no se reintentan.
  Log al deshabilitar: `gemini-key-N disabled: unauthorized`.
- Red, timeout o `5xx`: probar otra key elegible. Cooldown de 1 s exponencial
  hasta 60 s o `Retry-After` si está presente. Cada intento conserva el timeout
  existente: 20 s texto, 40 s imágenes. Una cancelación del padre detiene el failover.
- Bloqueo de contenido, payload malformado y errores locales/BD: no rotar para
  sortearlos. Un bloqueo no provoca llamadas extra.
- Pool sin keys elegibles: `LlmUnavailable` sanitizado, sin bucle ni espera
  activa. `429` agotado conserva kind `quota`; fallos técnicos/auth, `provider`
  o `timeout` según el último intento. Si ya estaba todo en cooldown, se comunica
  indisponibilidad temporal por la ruta normal. Los atajos siguen disponibles.

Los cooldowns globales antiguos de `llm_cooldowns` dejan de controlar Gemini; no se
borran filas/tablas históricas ni se agrega migración. Las protecciones locales
positivas conservan reserva atómica en BD, día Pacífico y conteo por intento.
Cada intento HTTP tiene fila propia en `llm_usage`, sin credencial, con el mismo
turnId y status/tokens reales si Google los reporta.

## Concurrencia y presupuestos R5

Se mantienen como máximo cuatro llamadas lógicas en vuelo por proceso (configurable),
incluyendo sus failovers secuenciales. Cola FIFO hasta 100 pendientes, espera máxima
20 s; no se rechaza solo porque los cuatro slots estén ocupados. Al exceder esa
espera/capacidad se usa `LlmUnavailable(local_limit, concurrency)`. Abort y errores
liberan el turno de cola/permiso; la espera no reserva uso ni envía HTTP.
App y worker tienen sus propios pools y límites; no hay coordinación distribuida.

`CallBudget.used` cuenta generaciones **lógicas**, manteniendo máximo tres por
turno; un failover no consume una nueva generación ni impide terminar el turno.
Los contadores existentes y calls per turn cuentan los intentos HTTP reales,
incluidos reintentos, para que el costo no quede oculto. Se preservan límites de
tools/capability expansion, exposición dinámica, Exact Fast Path y Local Presenters.
No se cambian permisos, schemas, router, Policy, Registry, ledger ni executor.

El adapter vuelve a enviar el mismo payload durante failover: content/parts,
firmas opacas, IDs de function calls y function responses. El pool no conoce ni
invoca tools. Cada nueva generación puede elegir otra key. Si se agotan las keys
tras ejecutar una tool, R5 conserva su ToolResult/recibo y presenta localmente;
no vuelve a ejecutar el efecto. `xp.daily` normal sigue presentándose localmente
sin generar una síntesis innecesaria.

## Métricas y diagnóstico

`diag.cuota` conserva el permiso global existente y muestra configuración efectiva,
keys configuradas/saludables/disponibles/cooldown, concurrencia/cola, calls hoy y
tokens de entrada/salida por modelo desde BD. Expone por índice requests,
successes, rate limits, failures y si está deshabilitada. Incluye failovers y
exhausted-pool events del proceso. No imprime keys ni fragmentos.

p50/p95 son latencias de los últimos 256 intentos del proceso; no incluyen espera
en cola y no son un histograma histórico persistente. Las métricas de pool son
locales al proceso consultado y se reinician; calls/tokens diarios y turnId siguen
persistidos en `llm_usage`. Las métricas R5 existentes conservan calls per turn,
tokens y latencia del router. No se guardan prompts en métricas.

## Límites del proveedor y fuentes verificadas

No hay cuota infinita. Google aplica cuotas **por proyecto**, no por API key;
varias keys del mismo proyecto pueden compartir todas sus cuotas. No se infiere
proyecto a partir del secreto ni se agregan proyectos, cuentas o facturación.
La rotación no garantiza disponibilidad ni aumenta la cuota real. No se implementa
ningún mecanismo para eludir bloqueos de cuenta/proyecto o contenido.

Verificado el 17-10-2026 en fuentes oficiales:
- [Cuotas Gemini](https://ai.google.dev/gemini-api/docs/rate-limits).
- [Errores Gemini](https://ai.google.dev/gemini-api/docs/troubleshooting).
- [API keys y autenticación](https://ai.google.dev/gemini-api/docs/api-key).
- [Errores estructurados Google](https://google.aip.dev/193).
- [Firmas opacas](https://ai.google.dev/gemini-api/docs/thought-signatures).

La validación usa HTTP simulado y BD efímera. No consume cuotas reales ni demuestra
que una firma emitida por un proyecto concreto sea aceptada por otro: si Google
rechaza una continuación, se conserva la respuesta local existente. Un failover
puede aumentar la latencia hasta la suma de deadlines de las keys intentadas;
no añade reintentos de la misma key ni llamadas fuera de la pasada acotada.
